# Worked examples (illustrative, do not copy)

## Florist cooler booking (generic)
**Ask:** "New look, same booking rules and staff/admin permissions."
**Makeover.** Direction: daylight, horticultural, green from their public CTA (provenance), serif on cover only, dense operate grid, moment = today column and cooler capacity.
**Preserve:** roles, booking named **action ids** and payload shapes, route ids, who can override a slot. Visible filter captions may be clarified; ids stay.
**Rearrange:** filters into one bar; week grid keeps the same actions.
**Not remix:** no new "route the van" feature.
**Live check:** do not click Book on connected inventory unless the user actually authorized that write; otherwise mark the fire blocked.

## CSS-only visual system (legitimate makeover)
**Ask:** "New look and feel; keep every page id, class, hook and named action."
**Makeover**, if site CSS actually changes type scale, spacing rhythm, hierarchy, component look and states. Unchanged schema/class names are expected and **not** a fail. Hue-only on the old type/spacing/components would be polish, not this.

## Hypothetical gap (invalid)
Agent drops an in-scope Print action and writes "owner can accept; rarely used." **Fail.** Either the action stays, it is outside agreed scope, or the owner explicitly accepted dropping Print in this run (quoted).

## Dispatch board that is merely messy
**Ask:** "Tighten this, we like it."
**Polish**, not makeover. If you wrote a replacement palette, you overreached; revert to polish.

## Win-back with a new module
**Ask:** "Show them a redesigned app plus a new intake wizard on mock data."
**Remix.** Makeover would restyle without the wizard. Hand off; do not implement the wizard here.
